# teacher-student によるドキュメント改善

**文書の分かりやすさを、低性能な読み手が正しく理解できたかで測る。** 高性能なモデルは行間を補って読めてしまうため、自分で読み返しても不足に気付けない。最も低性能な student が全問正解できる文書なら、人間の読み手にも伝わる。

| 役割         | エージェント  | モデル / reasoning | 担当                                               |
| ------------ | ------------- | ------------------ | -------------------------------------------------- |
| orchestrator | メイン        | —                  | 対象と読み手の確定、受け渡し、ループ管理、最終確認 |
| teacher      | `doc-teacher` | Opus / high        | 問題作成 → 文書執筆 → 採点・診断・書き直し         |
| student      | `doc-student` | Haiku / low        | 指定ファイルだけを読んで解答                       |

## 手順

### 0. 準備（orchestrator）

- [/git-ops](../git-ops/SKILL.md) に従って作業ブランチを切る
- **対象**（ファイル・関数・節）と **読み手像**（例: 「このリポジトリに初めて触る開発者」「アドオンの利用者」）を確定する。依頼から決まらなければユーザーに確認する
- **student に読ませるファイル** を決める。対象が README なら README だけ、docstring・コメントならそのモジュールのファイル。読み手が実際に目にする範囲に合わせる
- scratchpad に作業ディレクトリを作る（例: `<scratchpad>/teacher-student/<slug>/`）。問題と模範解答はここに置き、repo にはコミットしない

### 1. 問題の作成（teacher、文書より先）

`doc-teacher` を起動し、**段階 1 だけ** を指示する。渡すもの: 対象、読み手像、student に読ませるファイル、保存先の `questions.md` / `answer_key.md` のパス。

この時点では文書を書かせない。問題を先に固定することで、文書が「読み手に必要な理解」から逆算される。

返ってきた問題を orchestrator が確認する:

- 文書の一文を写せば答えられる想起問題ばかりになっていないか
- 答えが一意に決まるか
- 読み手像に対して的外れな問題がないか

問題があれば SendMessage で teacher に直させる。

### 2. 文書の執筆（teacher）

同じ teacher に SendMessage で **段階 2** を指示する（問題作成時の文脈を保つため、新規起動しない）。

### 3. 解答（student）

`doc-student` を **毎ラウンド新規に** 起動する（前ラウンドの記憶を持ち越させない）。渡すのは:

- 読むべきファイルの一覧
- `questions.md` の問題文（パスではなく本文をプロンプトに貼る）

**`answer_key.md` のパスや内容、teacher の意図、前ラウンドの結果は渡さない。**

### 4. 採点と書き直し（teacher）

student の解答全文を SendMessage で teacher に渡し、**段階 3** を指示する。

- **全問正解** → 5 へ
- **不正解あり** → teacher が書き直した後、3 に戻る
- **teacher が問題の欠陥を報告した** → orchestrator が妥当性を判断する。問題を直す場合は、それまでの正解判定もリセットして 3 からやり直す

**上限は 5 ラウンド**。超えたらループを止め、残った不正解の問題・teacher の診断・student の迷った点をユーザーに報告して判断を仰ぐ。

### 5. 最終確認（orchestrator）

- `git diff` を読み、**ロジックが 1 行も変わっていない**こと（diff がコメント・docstring・Markdown・説明文字列だけ）を確かめる
- 問題文や模範解答の言い回しが文書に写し込まれていないかを確かめる。写し込みがあれば、student を通すためだけの記述なので teacher に原理の説明へ書き直させ、3 からやり直す
- `just format` と `just test` を通す（`--doctest-modules` で docstring 内の例も検証される）
- ユーザーへ、ラウンド数、各ラウンドの正答数の推移、変更したファイル、teacher が報告したバグ・設計上の懸念を報告する

## やってはいけないこと

- **student に模範解答や採点基準を見せる**。テストとして成立しなくなる
- **student を使い回す**。前ラウンドの問題と文書を覚えていると、文書の改善ではなく記憶で正解する
- **問題を文書に合わせて易しくする**。問題の変更は欠陥の修正に限る
- **student を高性能なモデルに差し替える**。低性能な読み手に伝わることがこの方式の基準
