ドキュメント整備を頼まれても、**足りているなら足さない**。過剰なコメント・同義反復
の docstring は明示的に嫌われている。既存の docstring / コメントが十分なら「点検して
問題なし」と報告するのが正しい成果。

一方で、**根拠 (why) が実装と食い違っているコメントは直す対象**。「何を」しか書いて
いない冗長なコメントも同様。事実として成立しないコメントは、無いより悪いという扱い。

**Why:** このプロジェクトは CLAUDE.md の「シンプルさを優先」「外科的な変更」を
ドキュメントにも適用している。diff の全行がユーザーの要求からトレースできることが
判定基準なので、ついでの加筆は原則アウト。

**How to apply:**

- 「docstring / コメントの点検」依頼では、まず全部読んで **変更ゼロが妥当か** を判断する
- 直す対象は (a) 実装との食い違い (b) why のない what コメント (c) UI 文字列の分かりにくさ の 3 つに絞る
- 判断に迷う UI 文字列 (`bl_label` など) は変更せず報告に回す。`bl_idname` / プロパティ名 /
  `MODIFIER_NAME` の値は public surface なので絶対に触らない
- `tests/` 配下は原則対象外だが、**docstring のみ**と明示された場合は許可される
