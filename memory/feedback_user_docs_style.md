type: feedback
---

利用者向けの README / `docs/` は、pamiq-core（<https://mlshukai.github.io/pamiq-core/>、ソースは <https://github.com/MLShukai/pamiq-core>）のような **簡潔な言い切り口調** で書く。日本語では常体（「〜する。」「〜になる。」「〜できる。」）にする。

- **読む量を最小にする**。GUI は見ればわかるので、画面やスクリーンショットから読み取れること（ボタンの位置、図の番号の順序、既定で閉じている／常に見えているといった見た目の状態）は文章に書き直さない。書くのは、図からは読み取れない重要なこと（前提、落とし穴、挙動の規則）だけにする
- 前置き（「典型的な手順は次のとおり」「下の図の 1 → 2 → 3 の順」）や、書かなくても困らない補足（非対応バージョンで起きることの説明など）は削る
- 敬体（〜します）やブログ風の語りかけ（〜しましょう、〜ですね、〜でしょう）は使わない
- 箇条書きは体言止めを基本にする（例: 「体積を mL で計測」「同じ形のオブジェクトを作成」「別々のオブジェクトに分離」）。番号付き手順は「〜する。」でよい
- 1 文を短くし、1 文ごとに改行する。話題が変わるところでは空行で段落を分け、GitHub 上でも詰まって見えないようにする（GitHub の Markdown は、ただの改行を画面上の改行にしない）
- TL;DR は置かない（本文と重複して読む量が増える）
- 見出し・機能一覧・注意書きに絵文字を付ける（pamiq の「🎯 / ✨ / 🚀」や、絵文字付きの機能一覧のように）。付けすぎない
- 注意書きは `> ⚠️ **注意**: ...` の形の引用で書く。GitHub の `> [!WARNING]` 形式は、pre-commit の mdformat が `\[!WARNING\]` にエスケープして表示が壊れるので使わない

**Why:** 2026-09-29 に、最初の版（長い一文が続き、改行が少なく、絵文字もない説明調）について「私っぽくない」「改行が少なく、一文が長くて読みにくい」「絵文字も効果的に使うべき」と指摘された。いったんユーザーのブログ（geson-anko.github.io）寄りの語りかけ調に直したところ、「ブログ風ではなく pamiq-core 風の簡潔な言い切り口調が良い」と訂正された。形式は GitHub の Markdown のままでよく、MkDocs サイトは作らないことも確認済み。さらにユーザーが README を自分で添削し、「GUI は直感的なので、見ればわかるものは文章で書くべきではない」「人間が読む量はできる限り少なくする。図に書いてある情報は、重要でない限り文字で書き直さない」「箇条書き周りも自然な文体にした」と示した（同日、README から TL;DR・前置き・図の説明・5.0 非対応の説明を削り、機能一覧を体言止めにした）。

**How to apply:** 利用者向けの文書を書くとき・直すときに適用する。開発者向けの `CLAUDE.md` / skill / 仕様書は対象外（[[feedback_planning_doc_language]]）。利用者向け文書を書くタイミングは [[feedback_defer_user_docs]] に従う。
